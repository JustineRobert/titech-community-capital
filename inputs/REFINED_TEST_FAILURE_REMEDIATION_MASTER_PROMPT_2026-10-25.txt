The platform is financial technology infrastructure. Test-infrastructure changes must not weaken the real application contract to make tests green.

### Authentication, authorization, privacy and tenancy

Where affected paths touch these controls, preserve and test applicable behavior:

- JWT/session verification and access revocation.

- Institution/tenant isolation and cross-tenant denial.
- Input validation and safe failure responses.
- Audit events for security-sensitive actions.
- Privacy and consent enforcement where relevant.

### Payment and ledger invariants

Where affected paths touch financial workflows, verify the established lifecycle and contracts, including as applicable:

- Provider callback/status authenticity and validation.
- Payment idempotency and safe handling of duplicate requests/callbacks.
- Correct state transitions; unknown/timeout outcomes must not be silently treated as failure or success.
- Atomic business transaction and ledger posting where the architecture requires it.
- Double-entry debit/credit equality and currency-safe arithmetic.

- Audit traceability, settlement evidence, reconciliation of duplicate/missing/mismatched/late transactions, and period-close controls.

Use deterministic mocks for unit isolation where appropriate, but do not replace the real financial service with an always-successful mock to bypass assertions. Contract/integration tests must still prove the boundary they claim to verify. Distinguish provider simulation from real provider-sandbox evidence.

### Bootstrap, readiness and resilience

If tests cover bootstrap/startup, preserve dependency order, server lifecycle, route registration, middleware ordering, readiness behavior and graceful shutdown. Do not skip bootstrap phases merely because they make tests harder to load. A passing import/syntax test does not prove that the server starts, dependencies become ready, routes register, or the service is operational.

**Gate 3:** Review whether each source/config/test change could weaken security, tenant isolation, payment safety, ledger correctness, auditability, or startup behavior. Any relevant regression tests must pass or remain an explicit blocker.

## 8. REGRESSION TEST QUALITY STANDARDS

For each fix add or preserve an assertion that proves the defect cannot silently return. Examples:

- **Parser/syntax:** parser check plus real targeted suite execution.
- **Module classification:** actual test runner loads module in intended format.
- **Jest global:** test uses correct API in its real environment.
- **Mock ordering:** mocked dependency is registered before dynamically importing the ESM consumer where required.
- **Export contract:** named/default export assertions and tests for affected consumers.
- **Path resolution:** canonical source module is loaded; no accidental stub/duplicate is used.
- **Empty suite:** actual meaningful test registrations and business-relevant assertions exist.
- **Runner classification:** manifest proves ownership and the assigned runner executes the tests.
- **Duplicate/case variant:** coverage comparison and cross-platform path checks are recorded.
- **Open handles:** test owns/cleans resources and the process exits normally under diagnostic execution.
- **Financial regression:** applicable authorization, idempotency, ledger, reversal, settlement or reconciliation invariants are asserted.

Keep tests deterministic and isolated. Use existing conventions for database, Redis and provider dependencies. Do not invent production credentials, access external services unnecessarily, or store secrets in logs. Prefer controlled clocks, unique test data and explicit teardown where compatible with project conventions.

## 10. ACCEPTANCE CRITERIA

Mark **test-remediation complete** only when evidence demonstrates all applicable criteria below:

1. The full `mockLocalStorage.js` diagnostic is understood, and the parser/transform/runtime cause is corrected or transparently unresolved.
2. Each representative `require is not defined` failure has a proven module-context cause and is repaired at the correct boundary.
3. `jest is not defined` cases use the correct API/global setup for the actual runner and file format.
4. Missing default/named exports are resolved according to real module contracts and affected consumers are regression-tested.
5. Controller/model paths resolve to canonical implementations; cross-platform capitalization is checked.
6. Each empty-suite failure has a meaningful restored/repair test, a documented other-runner/helper disposition, or an evidence-backed retirement with replacement coverage.
7. Jest, Mocha and Vitest ownership is explicit; no unintended runner overlap or silent omission remains.
8. Duplicate and case-variant tests have evidence-based treatment and coverage is not lost silently.
9. Targeted regressions and all affected subsystem tests execute under the intended runner.
10. The agreed aggregate command covers all supported test families and has a captured final result.
11. Relevant resource cleanup is verified; unexplained open handles are resolved or explicitly outstanding.
12. Security, tenant isolation, payment safety, ledger invariants, auditability and startup behavior have not been weakened to achieve green tests.
13. No test is hidden using broad exclusions, dummy assertions, empty-suite suppression, unconditional skips, swallowed exceptions, or routine forced process exit.
14. The final Git diff preserves pre-existing work, contains no unexplained unrelated changes, and passes `git diff --check`.
15. Remaining failures, environment blockers and limitations are reported without relabeling them as passes.

**Zero test failures is not sufficient on its own.** A trustworthy result requires correct test discovery, meaningful assertions, complete runner coverage, reproducible evidence, and protection of the application contracts.

## 11. AUTONOMOUS WORKING METHOD

Proceed without asking the user to repeat facts already present. For each coherent repair batch:

1. Inspect the source/configuration and full error.
2. State the root-cause hypothesis in the failure register.
3. Validate the hypothesis using a targeted reproduction or inspection.
4. Make the smallest evidence-supported change.
5. Run the targeted regression test.
6. Inspect output and Git diff.
7. Update the register and proceed only when the exit gate is met or the blocker is documented.

If new evidence disproves a hypothesis, revise the register. Do not mechanically apply an earlier proposed fix. Prefer a narrow, well-supported fix that resolves a failure cluster over a broad change that merely changes the error message or removes the suite from discovery.

If repository access is unavailable, do **not** claim that code was edited, tests passed, or the result was verified. In that case, deliver the precise file-specific remediation plan, ready-to-run commands, and list of evidence that must be captured by the repository operator.

## 12. REQUIRED FINAL RESPONSE FORMAT

Report results in the following order:

1. **Execution status:** Completed, partially completed, or blocked, with evidence.
2. **Repository baseline:** Root, branch/commit, dirty state, runtime/runner versions, and whether the baseline was rerun.
3. **Confirmed root causes:** Separate from probable/unconfirmed hypotheses.
4. **Changes made:** Exact paths and concise explanation.
5. **Verification:** Commands, working directories, exit codes, counts, logs and actual outcomes.
6. **Before/after comparison:** Preserve the supplied baseline and explain any change in discovery scope.
7. **Security/financial regression assessment:** What was actually tested and what remains unverified.
8. **Outstanding defects and blockers:** Severity, affected functionality, evidence, and next action.
9. **Git readiness:** Working-tree state, diff check, and a proposed commit message; do not commit or push without authorization.
10. **Readiness verdict:** State separately whether syntax-validated, module-load-validated, test-validated, integration-validated, operationally validated, security-assessed, and production-approved. Use **NOT VERIFIED** or **BLOCKED** wherever sufficient evidence is absent.

### Final operating principle

**BUILD LESS. PROVE MORE. Fix root causes; preserve the architecture; keep tests meaningful; record the evidence; never claim a result that was not measured.**
